Claim-Verify Checkup

Five questions to identify which silent-failure pattern hit you. Each path ends with a specific cc-safe-setup hook to install and a pointer into the 49-case Claim-Verify Handbook.

A claim-verify gap is when Claude Code (or one of its sub-agents) says done while the underlying action failed silently. The tool layer reported success. The user's mental model says it's done. The system reality says otherwise — and there's no surface signal at the moment of divergence. Examples: a Write that was truncated, a goal evaluator that won't stop, a permissions.ask that never asked, a subagent that "fixed it" using a read-only tool.

DIAGNOSIS · virtiofs Write/Edit corruption

Your filesystem is silently null-padding or tail-chopping Claude Code's writes.

The Write tool returned success but the file isn't what was written. On virtiofs (Cowork's sandbox, some devcontainers, certain Docker setups), there are two known modes: shrink-then-null-pad (file size stays at the old, larger size with \x00 padding at the end) and grow-then-tail-chop (file is cut short at some boundary K below the intended length). The assistant believes the write succeeded; the next Read brings back corrupted content.
write-byte-integrity-verifier
PostToolUse #58551
After every Write or Edit, the hook reads the on-disk byte count and compares it to the intended content. If the file is larger than expected with trailing nulls, you get a shrink-pad warning. If smaller, a tail-chop warning. Edit additionally greps for new_string to confirm it landed.
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type": "command", "command": "~/.claude/hooks/write-byte-integrity-verifier.sh" }]
    }]
  }
}
DIAGNOSIS · general file integrity

On a regular filesystem, the byte-count verification hook still catches most surprises.

Even off virtiofs, the same pattern (assistant writes content, the file ends up wrong size, the Read returns something else) can happen due to permission errors, disk-full conditions, or symlinks pointing somewhere unexpected. The hook is cheap (~5ms) and catches the divergence at the moment it happens.
write-byte-integrity-verifier
PostToolUse #58551
Adds a byte-count check after Write and Edit, catches Write content vs file size mismatches and Edit's new_string not landing.
read-before-edit
PreToolUse #42796
Catches the broader "Claude edits files it never Read" pattern (Read:Edit ratio dropped from 6.6 to 2.0 in one analysis), which is often the upstream cause of writes that don't match the intended file state.
DIAGNOSIS · .env ANTHROPIC_API_KEY silently routing billing to API

Claude Code is billing your API account, not your Max plan.

If your project's .env contains ANTHROPIC_API_KEY=sk-ant-… AND your shell loads it (via direnv, source .env, etc.), Claude Code's child shells inherit it and the model client prefers env-var auth over the subscription. Anthropic has confirmed this is intentional design — the documentation is correct — so the only fix is on your side. Reported case: 9 auto-recharges totaling ~$187 USD, non-refundable.
dotenv-anthropic-key-billing-guard
SessionStart PSA 1tbaq2d
Scans your project for the 5 standard .env file names. If any contain a non-empty ANTHROPIC_API_KEY assignment, warns at session start with three concrete fixes: remove the line, set the env var to empty in your shell init, or move the key to a non-auto-sourced file.
{
  "hooks": {
    "SessionStart": [{
      "hooks": [{ "type": "command", "command": "~/.claude/hooks/dotenv-anthropic-key-billing-guard.sh" }]
    }]
  }
}
DIAGNOSIS · /goal evaluator with no iteration cap

A /goal kept firing after the condition became unsatisfiable.

The /goal evaluator runs after every assistant turn. With no built-in iteration limit, an unsatisfiable goal fires indefinitely. Reported case: 200+ iterations over 5 hours, ~50% of weekly token quota consumed. The assistant cannot clear a goal programmatically — only the user can with /goal clear. Workaround #4 from the issue: append or stop after N turns to your goal text.
goal-iteration-limit-warner
UserPromptSubmit #58550
Detects /goal commands at the moment of submission. If the goal text lacks a termination clause (heuristic scan for "stop after", "or stop", "max N", "N turns", "N iterations", etc.), warns with a recommendation to add one.
DIAGNOSIS · sub-agent doubling spend on the same tier

An advisor or sub-agent is calling the same expensive model as your main session.

When a sub-agent spawns its own Opus calls to "ask the advisor" or to plan, you pay the same per-token rate twice. Often invisible in the main /usage view. Issue #58217 documents the pattern. The cleanest mitigation is to constrain the sub-agent's model and tool allowlist explicitly in the delegation prompt.
subagent-tool-allowlist-enforcer
PreToolUse #55653 / #58217
Enforces a tool allowlist for sub-agent calls and surfaces the delegation prompt for review before spawn. Pairs with subagent-spawn-verification-enforcer for output verification.
DIAGNOSIS · permissions.ask bypassed for MCP tools

Your settings say "ask first" but the MCP tool ran anyway.

On Claude Code 2.1.139 (reported on Bedrock; likely affects other providers), entries in permissions.ask that match MCP tools (names starting with mcp__) execute without a confirmation prompt — same as if they were in allow. The MCP surface is exactly where many irreversible operations live (database writes, deployments, payment processing, message sending), making this gap especially costly.
mcp-permissions-ask-warner
SessionStart #58289
At session start, reads your settings.json (user + project), filters permissions.ask for mcp__* entries, and warns if any are found. Suggests three concrete workarounds: move them to permissions.deny (still gates correctly), use --permission-mode plan, or remove the entry.
DIAGNOSIS · auto-mode / allowlist bypass

A Bash invocation slipped through your allowlist or auto-mode gate.

The autoAllowBashIfSandboxed mode and similar gates have known prompt-pattern blind spots — for example, commands that contain key=value arguments or specific quoting can match in surprising ways. The cc-safe-setup destructive-cmd-guard family of hooks operates at the process level, after the gate decision, so they catch what the gate missed.
destructive-cmd-guard
PreToolUse #46058 / #49129 / #46684
Blocks rm -rf, dd, mkfs and similar destructive commands at the Bash invocation layer regardless of upstream gate decisions. Part of the standard cc-safe-setup install set.
auto-mode-safety-enforcer
PreToolUse #49618
Catches commands that match against an explicit safety pattern list, even in auto-mode-permissive contexts. Closes the gap left by the auto-mode classifier hardcoded to Opus 4.6.
DIAGNOSIS · destructive recovery after credential failure

The agent escalated to destructive commands "to fix" an auth error.

PocketOS-style pattern: a credential failure surfaces, the assistant interprets it as a state inconsistency, and proposes destructive operations (delete a volume, wipe a database, reset credentials) without re-asking permission. Once the destructive command runs, the original auth problem isn't fixed and now data is lost too.
post-credential-failure-destructive-guard
PreToolUse + PostToolUse PocketOS
Tracks recent credential or auth failures in the session and intercepts destructive commands that follow them, requiring explicit user confirmation before proceeding. 29 test cases.
DIAGNOSIS · sub-agent fabricating Write success on read-only tools

A research sub-agent reported "saved" while only having Read access.

The classic #55653 pattern. A spawned sub-agent without Write/Edit in its tool list returns text that says "I saved the changes to X" — language plausible enough that the parent agent treats it as truth. The user only discovers the gap when they read the file and find it untouched. The fix is on the parent side: verify each sub-agent's tool list before accepting its claim of having made changes.
subagent-tool-allowlist-enforcer
PreToolUse #55653
Inserts an explicit tool boundary into the delegation prompt and surfaces the parent-side verification steps to run after the sub-agent returns.
subagent-spawn-verification-enforcer
PostToolUse #55666
Forces the parent to verify the sub-agent's claimed outputs against actual file state and tool-call records before accepting "done".
DIAGNOSIS · sub-agent identity / context leak

A delegated agent leaked the parent's identity or history.

Issue #55488: sub-agents inherit conversational context they shouldn't. The sub-agent responds as if it were the main session, may reference details from threads it wasn't given, and can produce outputs that look like the parent's voice. For autonomous setups where the sub-agent is supposed to operate under tighter constraints, this collapses the safety boundary.
subagent-identity-leak-guard
PreToolUse #55488
Inspects the delegation prompt for identity-boundary markers and surfaces any leak surface in the prompt construction before the sub-agent spawns.
DIAGNOSIS · sub-agent reporting fabricated tool calls

The sub-agent reported tool calls it never actually made.

Issue #57878 documented this in concrete numbers: 150 sub-agent dispatches, every single one with zero tool-use count, yet the sub-agents reported having run bash/read/write. The parent agent had no surface signal of the divergence between claimed and actual tool use. This is the strongest known case in the family and forms one of the main-body cases of the Claim-Verify Handbook.
subagent-spawn-verification-enforcer
PostToolUse #57878 / #55666
Forces the parent to verify the sub-agent's tool-call records via the transcript before accepting any "done" or "fixed" claim. Pairs naturally with the parent-side verification steps in Chapter 8 of the handbook.
DIAGNOSIS · /usage dashboard token-count drift

The 7-day usage view doesn't match what you actually used.

Issue #58287 (2026-05-12, version 2.1.139, macOS): the /usage dashboard misreports input/output token counts for the 7-day period. This is a display-layer bug; no hook can fix the rendering, but you can compensate by tracking tokens with an independent logger.
prompt-usage-logger
PostToolUse #41249
Logs every prompt and response to a side file so you can reconstruct token consumption independently of the official dashboard. Pairs well with token-budget-guard for hard limits.
DIAGNOSIS · agents view false-pinning on background bash

The agents view says "Working" because a background process is still alive.

Issue #58297: a long-lived subprocess (a dev server, tail -f, a polling loop) makes the agents view believe the agent is still mid-turn, even when no model call is in flight. Pure display bug; a hook can't repaint the UI. The mitigation is to make sure background processes are tracked separately from agent state.
subagent-error-detector
PostToolUse #41911
Doesn't fix the display, but catches subagent errors that would otherwise be hidden behind the "Working" state, surfacing the real status from a different angle.
DIAGNOSIS · status line / context% display reset after /compact

The context% indicator went to 0 or disappeared after compaction.

Issue #58268 (and the broader compaction-related cluster): after /compact, the status line shows 0.0k tokens or the ctx% indicator disappears, even though the session continues with real context. Another display-only divergence — the underlying state is fine, the indicator is wrong. The right mitigation is to track context% with an independent monitor.
compact-alert-notification
PostToolUse #41788 / #58268
Notifies on every auto-compaction event so you have an out-of-band record of when context was compressed. Useful for reconstructing what the status line missed.
pre-compact-transcript-backup
PreCompact #40352
Backs up the full JSONL transcript before each compaction so you can recover the pre-compact state if something goes wrong.
