Safety Checkup

Seven questions to estimate how exposed your Claude Code setup is to irreversible-operation accidents — silent file overwrites, accidental data deletes, files leaving the machine. Built from May 2026 incident reports where real users lost real data. Takes 90 seconds. No tracking, no email.

Why now: May 6, 2026, Issue #56738 — Claude Code wrote a SQL script with a regex bug that deleted 24,472 of 24,475 rows (3 days of scraping work). Same week: #56759 (/export silently overwrote an existing file), #56739 (model bypassed CLAUDE.md restrictions and sent a personal file to a third-party API). The pattern is recurring. This checkup tells you where you sit.

Question 1 of 7 — Direct destructive access

What destructive operations can Claude Code reach in your current setup?

"Reach" = it can run the command without your approval, or you typically click approve without reading.

Direct DB access (psql, mysql, sqlite3) on real data
Production database, scraped dataset, anything you cannot easily recreate.
File operations on user data (rm, mv, find -delete)
Documents, Pictures, Desktop, source code outside the project.
File operations only inside one project tree
Bounded by CLAUDE.md or by sandboxing (Docker, devcontainer, restricted user).
Read-only or sandboxed
Claude Code cannot modify anything outside an ephemeral environment.

Question 2 of 7 — Hook layer

Do you have PreToolUse hooks gating destructive operations?

Hooks intercept tool calls before they run. Without them, the model's self-restraint is the only line of defense.

No hooks at all
Default Claude Code installation, nothing custom.
Some hooks, but not for destructive operations
Logging, formatting, lint — useful but won't stop a bad DELETE.
Hooks block one or two destructive patterns
e.g. block rm -rf but no row-count guard on SQL.
Comprehensive: SQL row counts, file overwrite checks, scope limits
Multiple PreToolUse hooks covering the destructive patterns Claude Code can invoke.

Question 3 of 7 — Backup recoverability

If Claude Code corrupted or deleted something important right now, how recently could you restore it?

"Restore" = you actually verified the backup works, not just "I think there's a snapshot somewhere."

No working backup
No tested restore path. Or backups exist but you have not actually restored from them.
Backup older than a week
Some recoverable snapshot exists but you would lose recent work.
Per-session snapshot
Git checkpoint, restic snapshot, or DB dump before each significant Claude session.
Continuous, tested, off-machine
Recoverable to within an hour, restore tested in the last 30 days.

Question 4 of 7 — Permission mode

What permission mode do you typically run Claude Code in?

Permission mode controls whether each tool call needs your approval before it runs.

Auto-approve everything
--dangerously-skip-permissions, or acceptEdits on, or "approve all" clicked at the start.
Click-through approve
Prompted for each tool call, but you usually click approve without reading carefully.
Review every tool call
You actually read each Bash command before approving.
Tight allowlist + manual review
Only specific tools or commands are pre-approved; everything else needs explicit review.

Question 5 of 7 — Scope

What can Claude Code see beyond your current project?

Issue #56739 (May 6, 2026) reported the model running find across the entire Desktop and sending an unrelated personal file to a third-party API.

Full home directory or Desktop
No filesystem restrictions; Claude Code can find, cat, or send anything in ~.
User data folders are reachable
Documents, Pictures, OneDrive, Dropbox folders are not blocked.
Project tree plus parent ancestors
Bounded but can climb up the directory tree (../../../).
Strictly project-scoped
CLAUDE.md scope rules + PreToolUse hooks that grep find paths and block escapes.

Question 6 of 7 — Dry-run discipline

When you ask Claude Code to clean, transform, or delete data, do you require it to count or test first?

Issue #56738's deleted 24,472 rows could have been caught by a single SELECT COUNT(*) before the DELETE.

Just runs
Tell Claude what to do, it writes the script, it executes. You see the result.
For "big" changes only
Production deploys, schema migrations — sure. Daily data cleaning — no.
Usually, when you remember
Goal is dry-run-first; in practice you skip when you are in a rush.
Always, automated
A hook or workflow forces a SELECT/dry-run before any DELETE/UPDATE/destructive action.

Question 7 of 7 — Past incidents

Have you experienced an irreversible Claude Code outcome you regretted?

Honest answer here calibrates the score. Most respondents have at least one near-miss.

Multiple times
Pattern is recurring; you have lost meaningful work or data more than once.
Once, lesson learned
It happened, you adjusted, but the structural fix is partial.
Near-miss, no actual damage
Caught it before it committed; or the recovery worked because of a recent backup.
Never
No irreversible regrets. Either you are early in adoption, or the controls in earlier questions are doing their job.
