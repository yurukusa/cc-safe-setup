Claude Code 捏造監査

並列のツール呼び出しのバッチが部分的にキャンセルされると、Claude Code は空いた結果の枠を、実行されていない出力で埋めることがあります。もっともらしいコマンドの結果、偽の「完了しました」、さらにはあなたが言ってもいない「あなたがこう言った」という偽のユーザー指示まで。実行されていないのに、実行されたように見える——これが、起票 #63538 で報告された、最も気づきにくい沈黙の失敗です。この道具は、あなた自身のセッションのログから、捏造の引き金になる並列バッチのキャンセルがいつ・何回あったかを数え、独立に検証すべきターンを特定します。すべてブラウザの中だけで動き、ファイルはどこにも送られません。

並列バッチのキャンセルのイベント(報告に使える時刻つき)

この時刻のターンで、並列のバッチの一部がキャンセルされました。直後の Claude の結果の報告(「完了しました」「テストは通りました」など)は、道具の報告をそのまま信じず、新しい独立した Read や再実行で確かめてください。キャンセルの後の報告こそ、捏造の疑いが最も濃い箇所です。

何が起きているのか

Claude Code は1つのターンで複数のツール呼び出しを同時に走らせます。そのうちの1つがエラーで終わるか、ハーネスがバッチをキャンセルすると、兄弟のツール呼び出しも一緒にキャンセルされ、結果が空、または「Cancelled」の通知として返ります(#64247 / #64047)。

その空いた枠を前にして、Claude は「何も実行されていない」と報告する代わりに、本来あるべきだった出力を生成してしまうことがあります。これが #63538 の挙動で、ここではツールの出力だけでなく、ユーザーの指示までもが捏造されました(言ってもいない「やめて、見直して」という指示が、本人の発言として報告書に書き込まれた)。#63884 では、並列のタスクが終わる前から結果を語り始めます。

これは「嘘をついている」のではなく、状態が曖昧なターンを、モデルが「欠落を認める」代わりに「もっともらしく再構成」してしまう構造的な問題です。Opus 4.8 に固有のものではありませんが、並列キャンセルの引き金がこの版でより目立つようになりました。

捏造を本物の結果から見分ける

合図示唆すること
ターンの途中で「Cancelled」「parallel tool call errored」の通知が出た同じバッチについて、その後で語られた結果はすべて疑わしい。1件ずつ単独で実行し直す
結果が不自然に綺麗・一般的・丸めてある(「すべてのテストが通った」「完了」)要約でなく、実際のコマンドと生の出力を見せるよう求める
エラーの後に echo test123 / echo alive のような生存確認が出るシェルが生きているか自信がない合図(#64247)。直後の主張は低信頼
ファイルを書いたと報告されたが、新しい Read が一致しないモデルの要約でなく、独立した読み取りで確かめる

確実な習慣は、新しい独立したツール呼び出しで結果を確かめること(新しい Read、コマンドの単独の再実行)。キャンセルを含んだターンの、モデル自身の語りを最後の言葉にしないことです。

今日できること(無料)

この挙動が出にくいモデルに固定する。 報告者は、捏造と労力配分の劣化が /model claude-opus-4-7 で解消すると述べています(#64153 の比較)。上流で並列キャンセルの経路が直るまでの、最も速い緩和策です。

大きな並列の同時呼び出しを避ける。 引き金は、部分的にキャンセルされたバッチです。危ない操作(リモートの ssh、不安定なコマンド)を大きな並列のバッチから分け、別々のターンに置くと、捏造で埋められる空欄の状況そのものが減ります。

そして、無料(MIT)の cc-safe-setup のフックで、行動に移す前に捏造や未検証の完了を検知できます: npx cc-safe-setup

関連するフックの例: fabricated-command-detector(実際に走ったものと一致しないコマンド出力を検知) / closure-word-verify-gate(検証のツール呼び出しが見えるまで「完了」の主張を保留) / dispatch-receipt(副作業者の作業に本物の受領を要求)。npm の依存はゼロで、フックは実行時に jq を使います。

「やったと言ったのに、やっていなかった」が繰り返し起きるなら。 主張と実態の検証ハンドブック($19・PDF)は、Claude Code とその副作業者が、実行時の実態と一致しない成功を主張した130件の記録です。3段階の検知の枠組み、14の運用側の防御、5つの検知の道具(すべて実装と試験済み)を収めています。まずは無料で: 上のフックと、プレビューのGist。多くの人は、まず上の無料のフックで足ります。

よくある質問

キャンセルが0件なら、捏造は起きていない?

並列バッチのキャンセルは、この道具が数える引き金です。0件なら、#63538 の型(キャンセル由来の捏造)の引き金は、このログには見当たりません。ただし捏造は他の経路(解析の失敗 #62123、状態の曖昧さ)からも起こり得ます。完了の報告は、引き金の有無にかかわらず、独立した検証を最後の言葉にするのが安全です。

この道具は捏造そのものを検出する?

いいえ、断定はしません。捏造かどうかは、その後の報告の中身を人が見て判断する領域です。この道具が確実に示せるのは、構造から読み取れる事実——並列バッチのキャンセルが起きた時刻と、結果が返らなかったツール呼び出しの数——だけです。それを使って、どのターンを優先して検証すべきかを絞り込みます。

「結果が返らなかったツール呼び出し」とは?

ログの中で、Claude がツールの実行を要求した(tool_use)のに、対応する結果(同じ tool_use_id の tool_result)がログに見当たらないものです。多くはセッションの末尾の進行中のものですが、ターンの途中で多発しているなら、その付近の報告は要検証です。

なぜ1つのエラーで並列の呼び出しが全部キャンセルされる?

その兄弟キャンセルの挙動は #64247 / #64047 で報告されています。これが空の結果の枠を作る上流の条件で、捏造はその下流の症状です。不安定な操作を大きな並列のバッチから外すと、起こる頻度が減ります。
