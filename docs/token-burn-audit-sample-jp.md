# 見本：Token Burn Audit（トークン浪費の監査）

これは実際の報告書だ。[¥3,980 の Token Burn Audit](https://yurukusa.github.io/cc-safe-setup/token-burn-audit-jp.html) の納品物そのものを、見本として公開している。

対象は私自身の使用記録——**セッションのログ156本、21,770回のAPIのやりとり**。自律で動かしている Claude Code の運用記録だ。お客さんのログにも同じ検査をかける。見本のために作った数字はひとつも無い。

測定は2026年8月9日 08:00 JST。測定している当のセッションが同じディレクトリへ書き続けているので、それは除外してある（理由は後述）。

> この文書は英語版 [`token-burn-audit-sample.md`](token-burn-audit-sample.md) と同じ内容の日本語版。数字も測定日も同じものを使っている。

---

## 0. 要点

**この監査が最初に見つけたのは、私自身の数え間違いだった——2.36倍の過大計上。**

Claude Code は1回のAPI応答を、JSONLの複数行（考えている部分・文章・ツールの呼び出し）に分けて書く。そして**同じ `usage` をその全部の行に複写する**。行ごとに足すと、1回のリクエストを何度も請求したことになる。`requestId` でまとめ直すと、**51,484行 → 21,770リクエスト**。

直した後の数字はこうだ。キャッシュの読み出しが推定請求額の **70.1%**。出力1トークンに対して、**231トークン**を読み返している。**支出の3分の2以上が、新しく書くためではなく読み直すために出ている**。

**このログで最大の浪費の型は、Token Book が載せている56の症状のどれにも当てはまらなかった。** そして**それを捕まえるはずだった自前のフックは、一度も鳴っていなかった**。どちらも、チェックリストからではなくこの監査から出てきた。

正直な逆側も書いておく。**みんなが真っ先に手を付ける「CLAUDE.md を削る」は、このログでは読み出し費用の約18%が上限だった。** 労力を売るより、上限を先に伝えたい。

## 1. トークンは実際どこへ行ったか

| | トークン | 推定額 | 割合 |
|---|---|---|---|
| 入力（キャッシュ外） | 1,527,528 | $23 | 0.1% |
| キャッシュ**書き込み** | 76,599,034 | $2,298 | 14.6% |
| **キャッシュ読み出し** | **7,384,839,143** | **$11,077** | **70.1%** |
| 出力 | 31,920,888 | $2,394 | 15.2% |

単価は仮定を置いた（百万トークンあたり 入力 $15 / 書き込み $30 / 読み出し $1.50 / 出力 $75）。
**あなたの実額は `/cost` に出ている。金額を口にする前に、私は必ずそちらと突き合わせる。**

自分のデータでまず確かめてほしい数字がひとつある。**キャッシュ書き込みの保持時間**だ。このログでは `ephemeral_1h_input_tokens` が 76,555,566 で `ephemeral_5m` が **0** だった。つまり1時間（2倍）の料率が効いている。あなたの環境が5分主体なら、割合はおよそ 読み出し75% / 書き込み8% / 出力16% へ動き、下の助言もそれに合わせて変わる。

## 2. 浪費の型・上位3件（費用の順）

### 型1 — セッションの中で1ターンの費用が2.2倍に伸びる（読む量は4.5倍）

やりとりが50回以上あったセッション101本を、順番に10等分した。

| 進行 | 入力トークン/回 | 1回の費用（込み） |
|---|---|---|
| 10% | 122,849 | $0.482 |
| **20%** | 182,142 | **$0.452** ← 最安 |
| **100%** | **550,604** | **$1.057** |

**読む量は4.5倍。費用は2.19倍**——読み出しの単価が安いぶん、差が圧縮される。両方の数字に意味がある。前者は文脈が膨らんでいることを、後者はそれがいくらかを教える。

**該当する第8章の症状：無し。** 56件すべて確かめた。症状3（`--resume` が前の文脈を復元する）は*開始点*の話、症状18（利用率の表示がずれる）は*表示*の話。**毎ターン全部を読み直すから費用が伸びる**という構造そのものを述べた症状は無かった。

その不在こそがこの商品の意味だ。カタログは「壊れたもの」を並べる。これは壊れていない——私が測った長いセッションでは毎回起きている。だからどの症状にも載らない。

### 型2 — 出力1トークンに対して231トークン読み直している

読み出し73.8億に対して出力3,192万。**セッションごとにこの比がどれだけ安定しているかは測っていない**ので、231は閾値ではなく桁として受け取ってほしい。

**第8章の症状1（プロンプトキャッシュの破壊）**は隣接するが同じではない。あちらはキャッシュが*無効化される*話。ここではキャッシュは正常に効いていて（入力側の99.0%が読み出し）、単に読み直すものが多い。

### 型3 — 読み出し÷書き込みの比が、101本で14から459まで開く

最小14.1、最大458.7。

**義務として書く但し書き：** 101本全部でこの比とやりとりの回数の相関を取ると、ピアソンの相関係数が **0.903** だった。つまり開きのほとんどは*セッションの長さ*で説明がつき、キャッシュの効率の差ではない。開きは見せられるが、2つの原因を分離することはまだできていない。**この開きを「あなたのキャッシュはそれだけ効いていない」と売る相手がいたら、それは読み過ぎだ。**

**第8章の症状1**はキャッシュを無効化するもの（`CLAUDE.md` の編集、`settings.json` の編集、MCPの接続と切断、`git status` の変化）を挙げている。このうちどれが効いたかは、この集計からは分けられない。

## 3. 型ごとの対策

### 型1への対策——そして、この監査を走らせる価値そのもの

`cc-safe-setup` は、文脈が膨らむ前に警告するはずのフックを配っている。この型に対して実際に走らせた。**鳴らなかった。**

| フック | 直す前の実測の挙動 |
|---|---|
| `context-usage-drift-alert` | 数える箱が*その日の全セッション*で共有され、150を超えるとその日は二度と鳴らない。ある日の2本目のセッション：**160回の呼び出しで警告0件** |
| `context-compact-advisor` | 200回の呼び出し → **「1」が入った箱が200個**。一度も積み上がらない |
| `session-duration-guard` | 100回の呼び出し → **「セッション開始」の記録が100個**。継続時間を一度も測っていない |
| `test-coverage-reminder` | 60回の呼び出し → 出力0 |

原因は、状態を保存するファイル名に `$$`（フックのスクリプト自身のプロセス番号）を使っていたこと。呼び出しごとに変わるので、状態が一度も残らない。[PR #972](https://github.com/yurukusa/cc-safe-setup/pull/972) で `session_id` を使うよう直した。直した後は、同じ実験で箱が1つになり、警告も正しく出る。

**2026年8月9日より前の版でこれらのフックを使っているなら、守られていない。** 更新してほしい。

フックに依存しない作業の直し方：**論理的な仕事ひとつごとに新しいセッションを始める。そして重い調査は、最初の数ターンの直後に置く**——いちばん安いのは第1十分位ではなく第2十分位だ（最初はキャッシュを作る費用を払っている）。

### 型2への対策

前置きに座っているものではなく、**1ターンが運ぶ量**を減らす。このログでは前置きの床が1ターンあたり中央値 **62,337トークン**あった（各セッションの最初の応答）。21,770ターンを掛けると13.6億トークンで、**全キャッシュ読み出しの18.4%**にあたる。

だから `CLAUDE.md`・ツールの定義・skill の説明を削るのは*無意味ではない*。**上限が5分の1**なだけだ。残りの5分の4は積み上がった会話——読んだファイル、ツールが返した結果、それまでのターン。請求が問題なら、こちらを先に切る。

### 型3への対策

長さと効率を分離できるまでは、防御できる行動は型1と同じ——セッションを短くする。キャッシュを無効化する変更（症状1）は、途中で挟まずまとめられるならまとめる。

## 4. 削減幅の見積り

このデータの読み出し費用 $11,077（約27日ぶん）に対して。なお**重複した指示の行を全部消すことは、この一覧に入っていない**。別に測った結果、それは **月 $0.24〜$1.19** の価値しかなかった。そこに金は無い。

| 打ち手 | 上限 |
|---|---|
| 前置きの床を半分にする | 約 $1,020（9%） |
| 文脈の伸びを3割抑える | 約 $3,320（30%） |

**これは上限であって予測ではない。** セッションの長さを半分にすれば、読む量も半分になるが仕事も半分になる。単一の数字を出すほうが不誠実なので、幅と上限で出している。

## 5. `cc-token-diet` の使い方

[cc-token-diet](https://github.com/yurukusa/cc-token-diet) は無料で、手元だけで動く。何も送信しない。**この監査を買う前に走らせてほしい。それで疑問が解けるなら、私は要らない。**

```sh
npx github:yurukusa/cc-token-diet --days 30
```

この機械では 550セッション / 87,943ターン / キャッシュ命中率98.0% と報告し、`runaway session(s) (>100 assistant turns)` を最大の費用として挙げた。**注意：このツールも2026年8月9日まで同じ「行ごとに数える」欠陥を持っていた**——この報告書を書きながら見つけて直した（この機械での見積りが $62,900 から $27,036 に下がった）。信じる前に更新してほしい。

見るべき点が2つある。ツールと監査の違いがここにある。

1. **ツールの数字と私の数字は一致しない。そしてどちらも正しい。** ツールは `~/.claude/projects/*/**.jsonl` を走査する——全プロジェクト、補助エージェントのログ込みで550セッション。上の私の数字は1プロジェクトの親セッションのみ（156本）を `requestId` でまとめたもの。**どちらも「その」数字ではない。あるのは「何を、いつ測ったか」だけだ。**
2. **ツールは型1を検出するが、定量化しない。** 「長いセッションは文脈を指数的に膨らませる」とは言う。読む量が4.5倍、費用が2.2倍、最安が第2十分位、とは言わない。**監査が測定で、ツールは煙感知器だ。**

**もうひとつ知っておく価値があること：** 補助エージェントのログは `<セッションID>/subagents/` の下にある。素朴な `*.jsonl` のパターンでは拾えない。ここではそれが **164ファイル、まとめ直して2,008往復——全ターンの8.4%**にあたった。私は最初の走査でこれを取りこぼし、後から直した。

## この監査がやらないこと

- **実装はしない。** 対策は提案であって、適用するのはあなた
- **削減額を約束しない。** 上限だけを、方法を見せた上で出す
- **仮定を測定として出さない。** 単価を仮定した箇所（第1節）はそう書き、あなたの `/cost` と突き合わせる
- **分離できない原因を主張しない**——型3を参照

## この報告書がどう作られたか

完成までに、私自身の数字が4つ間違っていた。最初の2つは**発見が大きく見える側**へ倒れ、残り2つは**範囲と精度の言い過ぎ**だった。

1. **JSONLを行ごとに足して、全トークンを2.36倍に過大計上していた。** `requestId` でまとめ直したら、やりとりの数が 51,484 から 21,770 に減った。注目してほしいのは、**この訂正が片方向に動かなかった**こと——*合計*は下がったが、読み出しの割合（64.9→70.1%）、出力あたりの読み直し（183→231）、セッション内の費用の伸び（1.83→2.19倍）は**すべて上がった**。定性的な結論5つは、ひとつも変わらなかった
2. 「費用が4.6倍になる」と書いたが、これは20倍の開きがある3種類の単価に1つの単価を当てた結果。正しく分けると **2.19倍**
3. 「全記録」と書きながら、補助エージェントのログ164本を黙って落としていた
4. 「最初の1割がいちばん安い」と書いたが、実際は**2割目**。最初の1割はキャッシュの作成を払っている

どれも、自分の要約からではなく**生のログから導き直して**見つけた。**その導き直しが、あなたが買っているものだ。** 集計は安いほうの半分でしかない。
