# 見本：Full-Surface Audit（運用の全面の監査）

これは実際の報告書だ。機微な行だけ伏せてあり、それ以外は手を入れていない。

対象は私自身の環境。自律で動く Claude Code のセッションを、毎日、並列で回している設定一式である。お客さんの環境にかけるのと同じ検査を、自分にかけた。

既に公開している2つの見本（[CLAUDE.md の監査](claude-md-audit-sample-jp.md)／[トークンの浪費の監査](token-burn-audit-sample-jp.md)）は、どちらも**1種類のファイルだけ**を見る。この監査はそこを変える。**5つの層を横断して、層と層の間に落ちている矛盾だけを拾う。**

なぜ横断するのかは、この報告書自体が答えになっている。**下の第2節の発見は、5つの層のどれか1つを丁寧に読むやり方では捉えられない。**どの層も、単独で見るかぎり正常だからだ。

測定日：2026-08-12。

## 0. 要点

**私が売っている安全網と、私を守っている安全網は、同じ名前の別のプログラムだった。**

配っている版だけが止める危険な書き方が、実測で **6つ** ある。私の環境はその6つを素通りさせる。しかも、そのうち3つは**私が実際に毎日打っている形**で、ログを数えると、`git push` を含む呼び出し **515件のうち502件（97.5%）** が、私の環境の柵が見ていない位置にあった。

そして「位置にあった」で止めずに中身まで読んだら、**本物の強制 push が2回、止められずに通っていた**（2026-08-09・機能ブランチ宛て・逐語で特定）。柵の説明文には「全てのブランチで強制 push を止める」と書いてある。

副次的な数字：登録されて動いているフックは **27本**（32箇所の登録）。そのうち、私が商品として配っているものと同じ名前のものが **4本** あり、**4本とも中身が違う**。差が最大のものは **稼働 8,319バイト／出荷 33,895バイト** で、約4倍。

**逆向きの漏れもある。** 1本だけは私の環境のほうが新しく、**お客さんには古い版が届いている**（第4節）。

**この監査が見つけ*なかった*もの：** 指示書と設定と CI の間には、実害のある矛盾が出なかった。第8節に、探して出なかったものを列挙する。

## 2. 発見1：配っている版と、動いている版が違う（重大）

### 事実

`settings.json` に登録されて実際に動いているフックのうち、私が `cc-safe-setup` として配っているものと同名のものが4本ある。**4本とも、稼働している実体と配布している実体の中身が一致しない。**

| フック | 稼働（最終更新） | 配布 | 差 |
|---|---|---|---|
| `destructive-guard.sh` | 8,319B（2026-05-27） | 33,895B | **+25,576** |
| `branch-guard.sh` | 2,616B（2026-05-27） | 4,447B | +1,831 |
| `secret-guard.sh` | 2,964B（2026-05-27） | 4,795B | +1,831 |
| `syntax-check.sh` | 3,889B（2026-07-27） | 3,152B | **−737**（逆向き・第4節） |

### 差が挙動として何を意味するか（対照つきの実測）

両方の実体に同じ入力を渡して、終了コードだけを読んだ。**実行はしていない。**

| 入力の形 | 稼働 | 配布 | |
|---|---|---|---|
| `rm --recursive --force <対象>`（旗の長い綴り） | 0 | **2** | ★配布だけが止める |
| `echo <base64> \| base64 -d \| sh`（難読化して渡す） | 0 | **2** | ★配布だけが止める |
| `ls <対象> \| xargs rm -rf`（`xargs` 経由） | 0 | **2** | ★配布だけが止める |
| `cd /tmp && git push --force origin main` | 0 | **2** | ★配布だけが止める |
| `npm test && git push origin main`（保護ブランチ） | 0 | **2** | ★配布だけが止める |
| `cd /tmp && git add .env` | 0 | **2** | ★配布だけが止める |
| `rm -rf <対象>`（**対照**・素朴な形） | 2 | 2 | 同じ |
| `git push --force origin main`（**対照**・単独の形） | 2 | 2 | 同じ |
| `git add .env`（**対照**・単独の形） | 2 | 2 | 同じ |

**対照を先に置いた理由**：この種の測定は、入力の渡し方を間違えると「全部素通り」という嘘の結果が簡単に出る。素朴な形が**両方で止まる**ことを先に確かめてあるので、上の6件は「撃ち方の誤り」では説明がつかない。

### なぜ単層では出ないのか

- **層3だけ**を読むと：稼働している `branch-guard.sh` の正規表現は `^\s*git\s+push` で、行頭に錨を打つのはごく普通の書き方に見える。これを単独で読んで「欠陥だ」と言う根拠はない。
- **層2だけ**を読むと：フックは正しく登録され、`matcher` も `Bash` で、参照先のファイルも全部実在する（実測：実体の無い登録は0件）。**設定の側は健全である。**
- **配布物だけ**を読むと：こちらは直っている。テストも通っている。問題は見えない。
- **並べて初めて**：同じ名前の2つの実体が別のプログラムで、**守りが弱いほうが私に適用されている**と分かる。

### 貼れる直し方

配布側は既に区切り対応の書き方になっている。稼働側へ同じ形を移すだけでよい。

```diff
-if ! printf '%s' "$COMMAND" | grep -qE '^\s*git\s+push'; then
+if ! printf '%s' "$COMMAND" | grep -qE '(^|;|&&|\|\|)\s*git\s+push'; then
```

```diff
-if printf '%s' "$COMMAND" | grep -qE '^\s*git\s+add'; then
+if printf '%s' "$COMMAND" | grep -qE '(^|;|&&|\|\|)\s*git\s+add'; then
```

**効くことの確かめ方**（自分の環境で30秒）：

```bash
j() { printf '{"tool_name":"Bash","tool_input":{"command":%s}}' "$1"; }
j '"cd /tmp && git push --force origin main"' | bash ~/.claude/hooks/branch-guard.sh; echo "終了コード=$?"
# 直る前は 0（素通り）。直った後は 2（拒否）。
```

## 6. 発見5：気づくための道具が、いちばん重要なファイルを見られなかった（重大・根本原因）

ここまでの第2節を読んで、当然の疑問が出る。**「差分に気づく仕組みは無いのか」。**

ある。`cc-safe-setup` には `--outdated` という命令があり、「入っているフックが、今日配っている版と一致するか」を照合して報告する。私が書いた。生まれた理由も、まさに今回と同じ症状だった（実装の注記に「4か月前の実機で、この企画由来の31本のうち27本が配布版と一致しなかった」と書いてある）。

**その `--outdated` が、第2節の4本を1本も見られない。**

実装は、入っているフックの置き場と `examples/` の中身を突き合わせる。ところが**中核のフックは `examples/` にファイルとして存在しない。**`scripts.json` の中の文字列として持っており、導入のときにそこから書き出される。

実測（実行はしていない。同梱物の構成を数えただけ）：

| | 場所 | 本数 |
|---|---|---|
| 中核のフック（既定で導入される） | `scripts.json` の鍵 | **11** |
| 任意のフック | `examples/*.sh` | 911 |
| **`examples/` に中核が在るか** | | **0本**（4本とも不在） |

`--outdated` の実装では、`examples/` に無い名前は「この企画が配っていないフック — 未確認」の側へ落ちる。つまり中核の柵が2か月半古いまま入っている利用者は、**「それはこの企画の関知するところではない」という趣旨の文言を返されていた。**

**これが第2節の原因である。**私の中核の柵が5月27日で止まっていたのは、注意不足ではない。**気づくための道具が、その4本だけを構造的に見られなかったからだ。**

### なぜ単層では出ないのか

- `--outdated` の実装だけを読むと：`examples/` と入っている物を突き合わせる、正しい照合に見える。
- 同梱物の構成だけを見ると：中核を `scripts.json` に置くのは、導入器がそこから書き出すので理にかなっている。
- **並べて初めて**：照合の対象と、導入の対象が、**同じ集合ではない**と分かる。

### 直した

この監査の結果として、同じ日に修正した。`--outdated` が `scripts.json` の中核も照合し、**該当したものに `[core guard]` の印を付ける**ようにした。あわせて `--show-core <名前>` を足した——中核は `examples/` に無いので、既存の `--install-example` では取り出せず、**名指しだけして取り出す手段が無い報告**になってしまうためである。

判別力の確認：新しい検査を**直す前の版へ当てて、中核に関する5件が落ちる**ことを先に見た。落ちない検査は、通っても何も言っていない。

## 7. 私の走査が間違えたところ（この工程が、あなたが買っているものだ）

機械の走査は素材で、報告書ではない。今回、自分の走査が最初に出した答えのうち、**手で当て直して取り消したものを全部書く。**

### 7a. 「登録27本のうち一致0本」は誤り

最初の集計は「登録されている27本のうち、配布版と一致するものは0本」と出した。**この言い方は誤りである。**27本のうち23本は**そもそも配布していない自作のフック**で、比較対象が存在しない。「一致0」は「23本が壊れている」と読めてしまう。

正しくは、**配布している同名のものが4本あり、その4本が全部違う**。母数を間違えると、同じ事実が6倍以上に膨らんで見える。

### 7b. 環境変数の指摘15件は、ほぼ全部が空振り

走査は「フックが読む `CC_*` の環境変数のうち、設定にも環境にも値が無いもの」を15件出した。1件ずつ読んだところ、**15件とも、値が無いときに安全側の既定で動く設計**だった（`CC_ALLOW_DESTRUCTIVE`、`CC_ALLOW_FORCE_PUSH` など、いずれも「設定すると守りが緩む」向きの変数）。**報告に載せる価値のある指摘は0件。**

機械の走査は「無い」を見つけるのは得意だが、**「無くてよい」を区別できない。**

### 7c. 「強制 push が8回素通りした」は、数え方も、その次に書いた訂正も間違えた

ログの突き合わせは「強制 push の形で止められずに実行されたもの8件」と出した。

**1回目の訂正**：8件を分類する走査を書いて「大半が偽陽性」と読み、**さらに `gh pr create -f` の `-f` を拾ったのが内訳だ、と具体名まで書いた。**

**2回目の訂正**：その具体名を確かめたら **0件** だった。分類の走査が当てにならないので、**8件すべてを、正規表現が当たった位置の前後200字ごと全文で読み直した。**

読み直した結果はこうだった。

| 何だったか | 件数 |
|---|---|
| コミットの本文・PR の本文・`python` のヒアドキュメント・フックの試験の記録の中に出てくる**文字列**（実行されていない） | **6** |
| **本物の強制 push。実行され、止まっていない** | **2** |

本物の2件は、どちらも同じ形をしている。

```
… MSG )" 2>&1; git push -q -f origin fix/session-scoped-counters-were-inert-2026-08-09 …
… 2>/dev/null; git push -q -f -u origin feat/token-burn-audit-sample-2026-08-09 …
```

**`;` の後ろにある。**だから `^\s*git\s+push` は当たらず、`branch-guard` の外側の判定は開く前に閉じた。どちらも 2026-08-09、機能ブランチ宛て（保護ブランチではない）。`git commit --amend` の後始末で、私が普通に打った形である。

`branch-guard.sh` の冒頭には、この動作についてこう書いてある。

> blocks force-push on ALL branches without explicit approval

**その約束が、2回、無言で破られていた。**

★**この節がこの報告書で一番長いのは、私が2回間違えたからだ。**1回目は数え方、2回目は「間違えた」と言うときの内訳。**分類を機械にやらせて、その分類を読まずに文章にした。**8件は全文を読める量だったのに読まなかった。

★**訂正の向きに注意してほしい。**私は最初、**実害を過大に**見積もり（8件）、次に**過小に**訂正した（0件・証拠なし）。**正しい値は2件で、どちらの訂正にも入っていない。**「多すぎた」と気づいたときに「ではゼロだ」へ振れるのは、慎重さではなく別の雑さである。

### 7d. 自分の指摘と食い違う記録が1件あり、そちらが正しかった

ログの中に「`npm test && git push --force origin main` を撃って**終了コード2を観測**」という過去の記録があった。今日の私の測定（素通り）と正面から食い違う。

**自分の測定と過去の記録が食い違ったら、食い違いの側を先に調べる。**今回はそれが最大の発見になった。

## 8. この監査が見つけ*なかった*もの

| `find <対象> -name '*.log' -delete` | 0 | 0 |
| `git filter-repo --path secrets --invert-paths` | 0 | 0 |

前者は、絞り込みのある `find` を許しつつ広い削除だけを捕まえる設計に注意が要るため、意図的に後回しにしてある既知の穴。後者は動詞の一覧に入っていない。**どちらも「直っている」と書けない。**

## 9. 影響順の上位3件

| 順 | 何を | どこへ | 効き方 |
|---|---|---|---|
| 1 | `--outdated` が中核も照合するようにする（第6節） | `cc-safe-setup` | **次に同じ漂流が起きたとき、機械が名指しする。**1と2を再発させない唯一の項目 |
| 2 | `branch-guard` と `secret-guard` の外側の判定に区切り対応を入れる（第2節の差分2つ） | `~/.claude/hooks/` | 実トラフィックの被覆が **2.5% → 100%**（`git push`）、**21.4% → 100%**（`git add`） |

（4番目に `syntax-check` の改良を配布物へ戻すこと。お客さんの側の検査が YAML と JS でも動くようになる。）

2と3は、**新しいコードを書く必要がない。**自分が既に書いて、既にテストして、既に配っているものを、自分の環境へ移すだけである。

**この報告書で一番高くついた事実はそこだ。**穴は知識の不足ではなく、**同じものが2箇所にあり、片方だけ直したこと**から来ていた。そして**片方だけ直したことに気づく道具は在ったのに、その道具の視界の外に、直すべき物が置かれていた。**

順位を1にしたのは、2と3が「今日の穴」なのに対し、1だけが「次の穴」に効くからである。**同じ報告書を来月もう一度書かなくて済むのは、1だけだ。**
